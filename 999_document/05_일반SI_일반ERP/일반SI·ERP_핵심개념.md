# 일반 SI·ERP 핵심 개념 — 인사(HR)·회계(FI) 중심의 정론과 실무 활용

> 기업용 업무 시스템(ERP)을 만들거나 고치는 SI 프로젝트에 처음 들어가는 개발자, 그리고 몇 년 해 봤지만 업무 지식을 정리해 두고 싶은 중급자를 위한 개념 정리다.
> 특정 회사·제품의 화면이나 테이블이 아니라 **어느 ERP에나 통하는 원리**를 적었다. 법정 계산식·세율·한도는 해마다 바뀌므로 실제 업무에서는 그해 법령과 고객사 규정으로 다시 확인한다.

## 한눈에 보기

| 영역 | 한 줄 핵심 | 개발자가 꼭 알아야 할 것 |
|---|---|---|
| SI 프로젝트 | 분석 → 설계 → 개발 → 시험 → 이행 → 안정화 | 산출물이 다음 단계의 입력이다. 요건 추적이 끊기면 마지막에 터진다 |
| ERP 전체 | 업무별 모듈이 **하나의 데이터**를 나눠 쓴다 | 한 모듈의 저장이 다른 모듈의 전표·재고·원가를 움직인다 |
| 인사(HR) | 사람의 입사부터 퇴직까지, 그리고 급여 | 발령 이력, 기준일, 급여 계산 순서, 개인정보 |
| 회계(FI) | 모든 거래는 결국 **전표**로 남는다 | 복식부기, 계정과목, 자동 분개, 마감 |
| 관리회계(CO) | 같은 돈을 부서·제품·프로젝트별로 다시 본다 | 원가 중심점, 배부 기준 |
| 물류(SD·MM·PP) | 판매·구매·재고·생산의 흐름 | 수주→출하→청구, 발주→입고→지급 |
| 공통 | 마스터 데이터, 결재, 권한, 인터페이스, 이관 | 공통이 흔들리면 모든 모듈이 흔들린다 |

## 1. SI 프로젝트의 흐름

| 단계 | 하는 일 | 주요 산출물 | 자주 터지는 곳 |
|---|---|---|---|
| 분석 | 현행 업무(AS-IS)를 듣고 바뀔 업무(TO-BE)를 정한다 | 요구사항 정의서, 업무 흐름도 | 「지금처럼 해 주세요」 뒤에 숨은 예외 업무 |
| 설계 | 화면·테이블·인터페이스·권한을 정한다 | 화면 설계서, 테이블 정의서(ERD), 인터페이스 정의서 | 코드값·기준일·이력 관리 방식을 정하지 않고 넘어감 |
| 개발 | 화면과 서비스, 쿼리, 배치를 만든다 | 소스, 단위 시험 결과 | 설계서와 실제 테이블이 어긋남 |
| 시험 | 단위 → 통합 → 사용자 인수 시험 | 시험 시나리오, 결함 목록 | 모듈 사이(인사 → 급여 → 회계 전표) 연결 시험 부족 |
| 이행 | 옛 시스템 데이터를 옮기고 운영으로 넘긴다 | 이관 계획서, 대사(맞춰 보기) 결과 | 건수는 맞는데 금액·잔액이 안 맞음 |
| 안정화 | 운영 중 결함을 고치고 넘겨준다 | 운영 매뉴얼, 인수인계서 | 「왜 이렇게 만들었는지」 기록이 없음 |

**실무 요령**
- 요구사항마다 번호를 붙이고, 화면·테이블·시험 시나리오까지 같은 번호로 이어 둔다(요구사항 추적표). 고객이 「이거 요청했잖아요」라고 할 때 근거가 된다.
- 설계서는 「정답」이 아니라 「합의의 기록」이다. 바뀌면 바로 고치고, 바뀐 이유를 한 줄 남긴다.
- 개발 환경과 운영 환경의 차이(데이터, 코드값, 권한)를 표로 관리한다. 개발에서는 되는데 운영에서 안 되는 결함의 절반이 여기서 나온다.

## 2. ERP의 기본 구조

ERP는 회사의 업무를 모듈로 나누지만, 데이터는 하나로 묶여 있다. 그래서 「통합」이 핵심이다.

| 모듈(관행상 약어) | 다루는 업무 |
|---|---|
| HR / HCM | 인사 기록, 조직, 발령, 근태, 급여, 평가, 교육, 퇴직 |
| FI | 재무회계 : 전표, 총계정원장, 채권·채무, 자산, 결산 |
| CO | 관리회계 : 원가 중심점, 손익 분석, 예산 |
| SD | 판매 : 견적, 수주, 출하, 청구 |
| MM | 구매·재고 : 구매 요청, 발주, 입고, 재고 이동 |
| PP | 생산 : 생산 계획, 작업 지시, 실적 |

**대표적인 두 흐름**
- **판매에서 수금까지(Order to Cash)** : 수주 → 출하(재고 감소) → 청구(매출 전표) → 수금(채권 정리)
- **구매에서 지급까지(Procure to Pay)** : 구매 요청 → 발주 → 입고(재고 증가, 미지급 전표) → 송장 확인 → 지급(채무 정리)

두 흐름 모두 **물건이 움직이는 순간 회계 전표가 자동으로 생긴다.** ERP 개발에서 「저장」 버튼 하나가 회계까지 이어지는 이유다.

## 3. 공통 기반 : 모든 모듈이 기대는 것

### 3-1. 마스터 데이터
- 사원, 조직(부서), 거래처, 품목, 계정과목, 코드 같은 **기준 정보**다. 거래 데이터(전표, 발주, 급여 내역)는 마스터를 참조한다.
- 마스터는 **이력**으로 관리하는 경우가 많다. 「언제부터 언제까지 유효한가」(시작일·종료일)를 갖고, 조회는 「기준일 시점의 값」으로 한다. 부서가 바뀐 사원의 지난달 급여는 지난달 부서로 집계해야 하기 때문이다.

### 3-2. 공통 코드
- 성별, 직급, 결재 상태처럼 화면마다 쓰는 선택 목록을 한 테이블(코드 그룹 + 코드값)에 모아 둔다.
- 코드값을 소스에 그대로 박지 않는다. 고객사마다, 연도마다 바뀐다.

### 3-3. 결재(전자결재) 연동
- 업무 문서(휴가 신청, 지출 결의, 발령)는 대개 「작성 → 결재 요청 → 승인/반려 → 확정」 상태를 거친다.
- 개발 포인트 : 결재가 끝나기 전에는 업무 데이터를 확정하지 않는다. 반려되면 무엇을 되돌리는지, 결재 중에 원본을 고치면 어떻게 되는지를 설계 단계에서 정한다.

### 3-4. 권한
- 「누가 어떤 화면에서 어떤 데이터까지 볼 수 있나」를 정한다. 메뉴 권한(화면 접근)과 데이터 권한(자기 부서만, 자기 사업장만)은 별개다.
- 인사·급여 데이터는 특히 좁게 연다. 시험 데이터라도 실명·주민번호·계좌번호는 가린다.

### 3-5. 인터페이스
- 은행(이체), 국세청(전자세금계산서·원천세), 4대 보험 기관, 그룹웨어, 다른 시스템과 데이터를 주고받는다.
- 개발 포인트 : 보내기 전과 받은 뒤의 건수·합계를 기록하고, 실패했을 때 다시 보낼 수 있게 만든다.

### 3-6. 데이터 이관
- 옛 시스템 데이터를 새 테이블 구조로 옮긴다. 순서는 **마스터 → 잔액(기초) → 거래 이력**이 기본이다.
- 검증은 건수만 보지 않는다. **금액 합계, 계정별 잔액, 사원별 누계**까지 옛 시스템과 맞춰 본다(대사).

## 4. 인사(HR)

### 4-1. 인사 기본
- **사원 마스터** : 인적 사항, 입사일, 소속, 직급·직위·직책, 재직 상태. 개인정보가 가장 많이 모이는 곳이다.
- **조직** : 부서 계층(회사 → 본부 → 부서 → 팀). 조직 개편은 이력으로 남겨야 과거 보고서가 깨지지 않는다.
- **발령** : 입사, 승진, 전보, 휴직, 복직, 퇴직이 모두 발령이다. 사원 마스터의 현재 값은 **발령 이력의 최신 결과**라고 보면 설계가 깔끔해진다.

### 4-2. 근태
- 출퇴근, 연장·야간·휴일 근무, 휴가(연차), 휴직을 기록한다.
- 근태 결과는 급여의 수당 계산으로 넘어간다. 근태 마감 → 급여 계산 순서를 지키지 않으면 수당이 틀린다.
- 연차 휴가 일수, 근로 시간 한도, 연장 근무 가산율은 근로기준법과 고객사 규정을 따른다. 법이 정한 최소 기준 위에 회사 규정이 얹힌다.

### 4-3. 급여
급여 계산은 대체로 다음 순서로 돈다.

1. **대상자 확정** : 그달 재직자, 입·퇴사자 일할 계산 대상
2. **지급 항목** : 기본급, 각종 수당(직책, 연장 근무 등), 상여
3. **과세·비과세 구분** : 식대처럼 한도 안에서 비과세인 항목이 있다
4. **공제 항목** : 4대 보험(국민연금, 건강보험, 장기요양보험, 고용보험), 소득세·지방소득세(간이세액표 기준), 기타 공제
5. **실지급액** = 지급 합계 − 공제 합계
6. **이체 파일과 급여 명세서**, 그리고 **급여 전표**(급여 비용 / 미지급금·예수금)

**실무 요령**
- 급여는 「다시 돌릴 수 있게」 만든다. 계산 → 확인 → 확정 단계를 나누고, 확정 전에는 몇 번이고 다시 계산할 수 있어야 한다.
- 소급 인상(지난달부터 인상 적용)은 「차액 계산」으로 처리하는 경우가 많다. 이미 지급한 달을 고치지 않고 이번 달에 차액을 얹는다.
- 원 단위 처리(버림·반올림·10원 단위 절사)를 항목마다 정해 두지 않으면 몇 원 차이 결함이 끝없이 나온다.

### 4-4. 연말정산
- 1년 동안 매달 간이세액으로 뗀 소득세를, 실제 공제 항목(부양가족, 보험료, 의료비, 교육비, 신용카드 등)을 반영해 다시 계산하고 차액을 돌려주거나 더 걷는다.
- 공제 항목과 한도는 해마다 바뀐다. 계산 로직을 코드에 굳히지 말고, 연도별 기준 테이블로 관리하는 설계가 오래 간다.

### 4-5. 퇴직금과 퇴직연금
- **퇴직금(법정 기준)** : 1년 이상 근무하면 받는다. 대략 `1일 평균임금 × 30일 × (재직 일수 ÷ 365)`로 계산한다.
- **평균임금** : 퇴직 전 3개월 동안 받은 임금 총액을 그 기간의 총일수로 나눈 값이다. 상여금·연차 수당을 어떻게 넣는지가 실무 쟁점이다.
- **퇴직연금** : 회사가 운용 책임을 지는 확정급여형(DB)과, 회사가 정해진 부담금을 넣고 운용은 근로자가 하는 확정기여형(DC)이 있다. 한 회사에 두 제도가 섞여 있기도 해서 사원별 유형 관리가 필요하다.
- **퇴직금 추계액** : 「지금 모두 퇴직하면 얼마를 줘야 하나」를 계산한 값으로, 회계의 퇴직급여충당부채 근거가 된다.

### 4-6. 평가·채용·교육
- **평가** : 평가 항목, 가중치, 평가자(1차·2차), 등급 환산, 보정. 점수는 「저장 당시 기준」으로 남겨야 기준이 바뀌어도 지난 평가가 흔들리지 않는다.
- **채용** : 공고 → 지원 → 서류·면접 전형 → 합격 → 입사(사원 마스터 생성)로 이어진다. 지원자 개인정보는 보관 기간이 끝나면 지운다.
- **교육** : 과정, 이수 기록, 법정 의무 교육 여부.

## 5. 회계(FI)

### 5-1. 복식부기와 전표
- 모든 거래는 **차변과 대변에 같은 금액**으로 기록한다. 예 : 현금으로 비품을 사면 차변 비품(자산 증가) / 대변 현금(자산 감소).
- **전표**는 이 기록의 단위다. 전표 한 장의 차변 합계와 대변 합계는 반드시 같다. ERP 개발에서 이것이 깨지면 무조건 결함이다.
- 계정과목은 크게 자산·부채·자본(재무상태표)과 수익·비용(손익계산서)으로 나뉜다.

### 5-2. 자동 분개
- 다른 모듈의 거래(급여 확정, 입고, 출하, 청구)가 저장될 때 **정해진 규칙대로 전표를 자동으로 만든다.**
- 규칙은 「어떤 거래 유형이면 어떤 계정을 차변·대변에 쓰나」를 표로 관리한다(분개 규칙, 계정 결정 테이블). 이 표가 비어 있거나 잘못되면 업무 화면은 정상인데 회계만 틀린다.
- 개발 포인트 : 업무 데이터와 전표를 **같은 트랜잭션**으로 묶거나, 따로라면 「업무는 저장됐는데 전표는 없음」 상태를 찾는 점검 쿼리를 둔다. 전표를 취소할 때는 지우지 않고 반대 전표(역분개)를 만드는 것이 원칙이다.

### 5-3. 채권·채무
- **채권(AR)** : 팔고 아직 못 받은 돈. 청구 → 수금 → 정리(반제).
- **채무(AP)** : 사고 아직 안 준 돈. 송장 → 지급 → 정리.
- 거래처별 잔액, 만기, 연체 관리가 핵심 보고서다.

### 5-4. 고정자산
- 취득 → 감가상각(정액법·정률법) → 처분. 감가상각은 매달 배치로 돌며 전표를 만든다.

### 5-5. 세금
- 부가가치세(매출·매입 세금계산서), 원천세(급여·사업소득), 법인세. 전자세금계산서는 국세청과 인터페이스한다.

### 5-6. 결산
- 월 마감 순서는 대체로 **각 모듈 마감(근태·급여, 재고, 판매) → 미결 전표 정리 → 감가상각·충당금 같은 결산 전표 → 장부 마감 → 재무제표**다.
- 마감된 기간에는 전표를 넣지 못하게 막는다. 마감 해제는 권한자만 하고 기록을 남긴다.

## 6. 관리회계(CO)와 물류 한 단락씩

- **관리회계** : 비용을 원가 중심점(부서)·손익 중심점·프로젝트에 붙여 「어디서 돈을 쓰고 어디서 버나」를 본다. 공통비를 나누는 **배부 기준**(인원수, 면적, 매출액)이 논쟁거리다.
- **판매(SD)** : 견적 → 수주 → 출하 → 청구. 단가 결정(거래처별 단가, 할인), 여신 한도가 주요 설계 포인트다.
- **구매·재고(MM)** : 구매 요청 → 발주 → 입고 → 송장 확인. 재고 평가 방식(이동평균, 선입선출)이 원가와 회계에 바로 영향을 준다.
- **생산(PP)** : 자재 명세(BOM), 공정, 작업 지시, 실적. 생산 실적이 재고와 원가를 움직인다.

## 7. 개발자가 자주 겪는 함정

| 함정 | 증상 | 예방 |
|---|---|---|
| 기준일을 안 정함 | 부서·직급이 바뀐 사원의 지난 자료가 지금 값으로 나온다 | 이력 테이블과 「기준일 조회」를 설계에 명시 |
| 코드값 하드코딩 | 고객사·연도가 바뀌면 소스를 고쳐야 한다 | 공통 코드·기준 테이블로 뺀다 |
| 원 단위 처리 불일치 | 화면 합계와 명세서·전표 합계가 몇 원 다르다 | 항목별 절사·반올림 규칙을 문서로 정한다 |
| 자동 분개 규칙 누락 | 업무 화면은 정상인데 전표가 안 생기거나 엉뚱한 계정 | 거래 유형 × 계정 표를 시험 시나리오에 넣는다 |
| 마감 무시 | 마감된 달에 전표가 들어가 재무제표가 바뀐다 | 저장 시 마감 여부 점검 |
| 재계산 불가 | 급여·정산을 한 번 돌리면 되돌릴 수 없다 | 계산 → 확인 → 확정 단계 분리 |
| 이관 대사를 건수로만 | 운영 첫 달 잔액이 안 맞는다 | 금액·잔액·누계까지 대사 |
| 개인정보 노출 | 시험 데이터·로그에 실명·주민번호가 남는다 | 가림 처리, 로그 금지 항목 지정 |

## 8. AI 도구(클로드 코드 등)를 SI 실무에 쓰는 법

### 8-1. 잘 맞는 일
- **요구사항 정리** : 회의록을 요구사항 표(번호, 내용, 근거, 확인 필요)로 바꾸게 한다. 「확인 필요」 칸을 꼭 만들게 해서 AI가 빈칸을 지어내지 못하게 한다.
- **설계서와 실제 대조** : 테이블 정의서와 실제 DB 컬럼, 화면 설계서와 실제 화면 항목을 비교해 차이 목록을 만들게 한다. 사람이 눈으로 하면 가장 많이 놓치는 일이다.
- **쿼리 초안** : 조회·집계 쿼리 초안을 쓰게 하고, 사람이 실행 계획과 결과 건수로 검증한다.
- **시험 시나리오** : 업무 규칙(예 : 「입사 1년 미만은 퇴직금 없음」)에서 경계값 시험 사례를 뽑게 한다. 1년 하루 전, 딱 1년, 1년 하루 뒤처럼.
- **이관 대사 쿼리** : 옛 시스템과 새 시스템의 건수·금액·잔액을 맞춰 보는 쿼리를 쓰게 한다.
- **인수인계 문서** : 소스와 설계서를 읽고 「무엇을, 왜 이렇게 만들었나」를 정리하게 한다.

### 8-2. 지켜야 할 선
- **고객사 데이터와 소스는 계약과 보안 규정이 허락하는 범위에서만** AI에 넣는다. 확인 전에는 테이블 구조만, 그것도 이름을 가린 예시로 쓴다.
- 실명, 주민번호, 계좌번호, 급여액 같은 개인정보는 AI 대화에 넣지 않는다.
- 운영 DB에 직접 쓰기(수정·삭제) 권한을 AI 도구에 주지 않는다. 읽기 전용 계정, 그것도 개발 DB부터 쓴다.
- 법정 계산(퇴직금, 4대 보험, 세금)은 AI의 답을 그대로 믿지 않는다. 그해 법령·고시 원문과 고객사 규정으로 확인한다.

### 8-3. 지시 틀 예시

```
목표 : 퇴직금 계산 쿼리 초안
입력 : 테이블 구조(컬럼 이름과 뜻만, 실제 데이터 없음)
규칙 : 1년 미만 제외, 평균임금은 퇴직 전 3개월 기준, 원 미만 절사
끝 기준 : 경계값 시험 사례 6개와 각 사례의 기대 결과를 함께 낼 것
모르면 : 컬럼 뜻이 불분명하면 추측하지 말고 질문할 것
```
