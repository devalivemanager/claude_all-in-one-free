# 검증 루프

> 원 출처 : 방구석컴퍼니 「AI 검증 루프 키트」(무료 배포 키트, 2026-09-29 · 바탕 : Boris Cherny, Y Combinator 강연 2026-07-27). 원 키트는 이 묶음에 들어 있지 않다. 지시문 원문과 화면 비교 검사기는 원 배포처에서 받는다.
> 이 스킬은 원 키트를 **작업에 쓰는 순서로 추리고**, 다른 자료에서 얻은 교훈을 덧붙인 것이다(각 줄 끝 괄호가 출처).

**한 줄 원칙** : 확인 수단을 주면 AI가 스스로 고친다(원 키트 실험 75→90점). 단 검사기는 **자기가 재는 것만** 좋아지게 하므로, 사람이 눈으로 볼 곳을 함께 건다.

## 1. 일을 시작할 때 : 네 줄 틀을 채운다

과제를 받거나 맡길 때 아래 네 칸이 비어 있으면 **시작 전에 채운다.** 사용자에게 받은 요청이 비어 있으면 직접 채운 안을 보여 주고 확인받는다.

```
[과제]        결과물 한 줄
[지켜야 할 선] 하면 안 되는 것 2~3개
[확인 방법]   맞았는지 알 기준·예시·비교할 원본 + 끝내기 전 눈으로 볼 곳 3개
[끝나는 조건] 기준 통과, 또는 N번 고쳐도 안 되면 멈추고 무엇이 막혔는지 보고
```

- **확인 방법이 가장 중요하다.** 없으면 「다 된 것 같다」에서 멈추고, 사람이 틀린 곳을 찾아 다시 시키게 된다
- **끝나는 조건에는 반드시 상한**(횟수)을 둔다. 상한에 닿으면 계속 고치지 말고 막힌 곳을 보고한다
- **정답지의 정밀도를 먼저 확인한다** — 비교 기준 자체의 오차가 끝나는 조건보다 크면 판정이 불가능하다(예 : 초 단위로 버린 기준 자막으로 「1초 이내」를 재려 한 일). 정답지가 거칠면 조건을 풀거나 정답지부터 만든다 `[작성자 시험 실패 사례]`
- **착수 전에 일의 크기를 선언한다** — 탐색 / 범위 한정 / 구조 변경 중 하나. 애매하면 무거운 쪽을 고르고, 작업 중에는 올리기만 한다. **승인은 그때 보여 준 단계에만 유효하다**(설계 승인 ≠ 구현 승인) `[superpowers brainstorming에서 이식]`

## 2. 루프를 돌릴 때

1. 만든다 → 2. 확인 수단으로 잰다 → 3. **결과물(비교 이미지·출력)을 직접 열어 본다** → 4. 다른 곳을 하나 고친다 → 1로
2. 점수가 기준을 넘어도 **눈으로 볼 곳 3개를 하나씩 예/아니오로 적는다.** 아니오가 있으면 계속 고친다
3. **내용과 상관없는 부분(배경 무늬·모눈선 등)으로 점수를 올리지 않는다** — 원 키트 실험에서 점수를 가장 크게 올린 것이 배경 모눈이었다
4. 보고에는 최종 점수·시도 횟수·눈으로 본 3곳의 판정을 함께 적는다
5. **증거는 이번 메시지에서 새로 실행한 결과만** 인정한다(이전 실행·「될 것이다」는 불인정). 주장마다 맞는 증거를 쓴다. 린터 통과 ≠ 빌드 성공, 테스트 통과 ≠ 요구 충족 `[superpowers verification-before-completion]`
6. **테스트 품질** — 기대값은 손으로 확인한 값으로 쓴다(대상 코드로 계산한 거울 단언 금지). 상수·문구만 지키는 변경 감지 테스트 금지. 끝내기 전 전체 테스트를 돌리고, 직접 만들지 않은 실패도 이름으로 보고한다 `[superpowers test-driven-development]`
7. 타이밍 문제는 sleep·timeout을 늘리지 말고 **조건이 될 때까지 폴링**한다 `[superpowers systematic-debugging]`
8. 문제가 생기면 「고쳐 줘」로 바로 들어가지 않는다. **범위를 좁히고(이 부분만), 원인을 한 줄로 말할 수 있을 때까지 분석한 뒤** 고친다. 범위를 안 짚으면 여기저기 건드리다 새 실수를 만든다 `[영상 학습 : 999_document/03_AI미디어_영상음성/AI미디어_영상음성_핵심정리.md]`
9. **검사하는 쪽도 실패한다.** 판정을 못 내렸거나 판정이 비어 있으면 통과가 아니라 **실패**로 센다. 「에러가 없다」는 「통과했다」가 아니다. 판정 없이 조용히 멈춘 검사를 통과로 착각한 실제 사례가 있다. 판정이 빠지면 검사를 다시 돌린다 `[LLM 위키 강연, 메타코드M 2026]`
10. **검사 기록이 없으면 차단이 기본값이다.** 다음 단계(발행·완료 보고)는 검사 기록이 있을 때만 연다. 검사 담당 하위 에이전트에게는 읽기 도구만 준다. 「고치지 마라」는 프롬프트보다 도구를 안 주는 쪽이 확실하다(스스로 고치고 스스로 통과시키는 것을 막는다) `[같은 출처]`

## 3. 지적이 쌓이면 : 승격 규칙(같은 실수를 두 번 겪지 않기)

사람의 지적(피드백·「또 틀렸다」)은 그때 고치고 끝내지 않고, **반복되면 한 단계씩 올린다.**

| 단계 | 조건 | 할 일 |
|---|---|---|
| ① 기록 | 지적이 처음 나옴 | 고치고, 지적을 한 줄로 남긴다(지시서·메모·`rules-log.md`) |
| ② 규칙 | **같은 지적이 두 번째** | 규칙 파일(지시서·CLAUDE.md·스킬)에 올린다. **이유 한 줄을 반드시 붙인다.** 금지만 적으면 빠져나갈 길을 찾고, 이유를 적으면 그 이유를 지키려 한다 |
| ③ 자동 검사 | 규칙을 **기계가 확인할 수 있음**(측정·대조·파일 검사) | 검사 스크립트로 만든다. 이후 사람이 다시 말하지 않아도 매 바퀴 돈다 |

- 검사 이름은 **앞머리로 묶어 목차로** 쓴다(`qa_ui_*`, `qa_spawn_*`, `check_blog_*`). 평소에는 **고친 곳과 이름이 겹치는 검사만** 돌리고, 정해 둔 주기(하루 한 번 등)에 전체를 돌린다. 이름만 보고 고르면 놓치는 것이 생기기 때문이다
- 검사는 세 종류를 섞는다 : **자동 검사**(몇 초면 재는 것) · **시각 검사**(캡처를 직접 읽기 : 그림이 맞나) · **사용 검사**(실제로 해 보기 : 쓸 수 있나). 코드가 멀쩡해 자동 검사를 통과하는 문제는 시각 검사로, 화면은 멀쩡한데 동작이 틀린 문제는 사용 검사로만 잡힌다
- 승격은 늘리기만 하지 않는다. 5절 규칙 다이어트처럼 **두 번 이상 적힌 것만** 규칙이 되므로, 한 번뿐인 지적으로 규칙을 만들지 않는다
- 근거 : 자율 루프·QA 영상 정리본(`999_document/02_게임개발/게임개발_핵심정리.md` : 「같은 지적 두 번 → 규칙, 확인 가능하면 QA」, 「규칙마다 왜 한 줄」)

## 4. 화면 재현 과제 (참고 화면을 HTML로 똑같이 만들 때)

- 확인 수단은 **참고 화면과 재현 화면을 찍어 겹쳐 비교하는 검사기**다(원 키트의 검사기를 쓰거나, 브라우저 캡처 + 이미지 비교로 직접 만든다). 출력은 일치 점수 + 기준·재현·차이를 나란히 놓은 비교 이미지로 받는다
- ★**점수가 무엇을 재는지 먼저 확인한다.** 원 키트 검사기의 총점은 배치(내용이 있는 자리의 겹침)만 반영하고, 색 일치도는 따로 출력될 뿐 총점에 들어가지 않는다 → 색은 눈으로 볼 곳에 넣는다
- 재현 과제에서 참고 이미지 파일이나 그 픽셀 데이터를 페이지에 넣는 것은 반칙이다. 직접 그려서 재현한다

## 5. 규칙 다이어트 (CLAUDE.md·스킬)

사용자가 규칙 파일을 줄이자고 할 때만 쓴다. **파일은 지우지 않는다.**

1. `CLAUDE.md`를 `CLAUDE.md.bak`으로 이름만 바꿔 백업하고, 규칙을 한 줄씩 번호 붙여 보여 준다
2. 규칙 없이 일하는 동안 사용자가 「또 틀렸다」고 하면, 백업의 몇 번 규칙과 관련 있는지 `rules-log.md`에 날짜와 한 줄로 적는다
3. **같은 번호가 두 번 이상 적힌 규칙만** 새 `CLAUDE.md`에 되살린다
4. 체크 : 되살린 줄이 원래의 절반을 넘으면 기준이 느슨한 것이다
5. 스킬 description에는 **언제 쓰는지만** 쓰고 절차를 요약하지 않는다. 요약하면 에이전트가 본문 대신 요약만 따른다. 규칙은 스킬 없이 돌린 실패를 먼저 본 뒤 그 실패에 맞는 형태로 쓴다 `[superpowers writing-skills]`

★프로젝트 `CLAUDE.md`가 「사용자 명시 요청 없이 수정 금지」를 두고 있으면 그 규칙이 우선이다. 이름 바꾸기도 수정이다. 사용자 확인을 받고 한다.
