# 루프 엔지니어링

> 근거 : 작성자 프로젝트에서 쓰던 에이전트 루프 9규칙(프로젝트 고유값 제외) · arXiv 2608.21884 「Loop Engineering: Building Blocks, Adoption, and Impact」 ·
> 분석 루프 형식 BHIAZT-SYS-01(차원 × 재귀 깊이 분석 틀)을 보완한 판(§3)

**정의** : 에이전트에게 한 턴씩 직접 지시하는 대신, **지시·검증·재시도·중단을 대신 결정하는 구조**를 설계하는 일이다.
프롬프트 → 컨텍스트 → 하네스 → 루프 순으로 한 겹씩 감싸며, 앞 단계를 대체하지 않는다.

**한 줄 원칙** : 루프는 **멈추는 조건 · 독립된 검증 · 디스크의 상태 · 사람에게 넘기는 지점**이 있어야 루프다. 이 넷이 없으면 같은 실수를 자동으로 반복하는 장치일 뿐이다.

## 1. 루프의 세 종류 — 무엇을 돌리는가

| 종류 | 무엇이 반복되나 | 어디에 적혀 있나 |
|---|---|---|
| **검증 루프** | 만들기 → 재기 → 고치기 (과제 하나) | 과제마다 확인 방법·끝나는 조건을 정해 둔다 |
| **실행 루프** | 일 찾기 → 처리 → 검증 → 다음 일 (일정·이벤트로 무인 실행) | 이 문서 §2 |
| **분석 루프** | 주제를 여러 축으로 펼치고, 축마다 핵심 변수를 따라 깊이 파고든 뒤 교차 종합 | 이 문서 §3 (BHIAZT 보완판) |

## 2. 루프 설계 — 착수 전 8질문

하나라도 「아니오」면 루프부터 만들지 말고 그 칸부터 채운다.

1. **완료를 기계가 판정할 수 있나** — 사람 판단 없이 통과/실패가 갈리는가. 흐리면 계약(체크리스트·테스트)부터 쓴다
2. **만드는 쪽과 판정하는 쪽이 다른가** — 자기 채점은 아첨으로 수렴한다(자기평가 58.2% 아첨, Fanous 2025). 판정은 다른 서브에이전트·다른 모델·실행 결과로
   - **판정하는 쪽** : 「판단 보류 목록」(범위 밖이라 제쳐 둔 것과 이유)을 반드시 낸다. 스펙이 말하지 않은 것이 허용은 아니다 — 심각도는 사용자가 겪는 영향으로 매긴다
3. **상태가 디스크에 있나** — 한 일·남은 일·실패한 일을 파일에 쓴다. 모델은 실행 사이에 잊고, 디스크는 기억한다
4. **재시작이 싼가** — 오염된 실행은 덧대지 말고 버린다(이어붙일수록 성공률 하락 : 1회 61% → 8회 25%, τ-bench)
5. **범위가 좁은가** — 첫 루프는 지루한 일 하나. 야심은 세 번째 루프에서
6. **위험한 일은 사람에게 남는가** — 배포·스키마 변경·삭제·외부 발송은 승인 지점을 둔다(프로젝트 `CLAUDE.md`의 사람 확인 규칙)
7. **원시 기록(트레이스)을 남기고 읽는가** — 이상하면 더 돌리기 전에 원문 로그부터 읽는다
8. **멈춤 장치가 있나** — 최대 반복 수 · 토큰/시간 예산 · 같은 실패 반복 시 중단 · 일시정지/해제 방법

**구성 블록** : 트리거(일정·이벤트) · 기계 판정 가능한 멈춤 조건 · 상태 파일 · 검증 서브에이전트 · 토큰 예산 · 사람 에스컬레이션 지점 · (병렬이면) worktree 격리 · 반복 지식은 스킬로

## 3. 분석 루프 — BHIAZT-SYS-01 보완판

### 3-1. 기본형의 구조

주제 하나를 **가로(차원 V 4개)** 로 펼치고, 차원마다 **세로(재귀 깊이 D)** 로 「핵심 변수 → 그 변수의 2차 파급」을 따라 내려간 뒤, 마지막 깊이의 노드끼리 **교차 종합**한다.
기본 차원 : v1 산업·경제적 파급 · v2 기술·인프라 구조 · v3 사회·윤리적 비용 · v4 거버넌스·규제. 핵심 변수 추출기 E 는 매 단계 「레버리지가 가장 높은 병목·변수 1개」를 강제로 뽑는다.

**장점** : 한 갈래로 쏠리는 분석을 막고(가로), 1차 효과에서 멈추지 않게 하며(세로), 차원 간 모순을 드러낸다(종합). 매 단계 변수 1개로 좁혀서 발산을 막는다.

### 3-2. 기본형 그대로 쓰면 걸리는 결함 → 보완

| # | 결함 | 결과 | 보완 |
|---|---|---|---|
| 1 | **검증이 없다** | d=0 의 k 가 틀리면 그 아래 전부가 오염된다(오류 누적) | 매 k 에 근거 라벨 `[실측]`·`[추측]`·`[확인 못 함]`. `[확인 못 함]` k 는 내려가기 전에 확인하거나, 표시하고 그 갈래를 멈춘다 |
| 2 | **갈래가 독립적이지 않다** | 한 컨텍스트에서 4갈래를 돌리면 앞 갈래가 뒤 갈래를 끌고 간다. 종합도 자기 채점 | 중요한 주제는 갈래별 새 컨텍스트(서브에이전트) + 종합 검토는 다른 주체 |
| 3 | **「상관 계수」는 가짜 정밀도** | 데이터 없이 LLM 이 낸 숫자는 계산이 아니라 지어낸 값 | 정성 행렬(강화 + / 상충 − / 무관 0) + 한 줄 근거. 숫자는 실제 데이터가 있을 때만 |
| 4 | **깊이 번호가 어긋난다** | 루프는 `d < D` 라 R[v][D-1] 까지만 만드는데, 종합은 R[v][D] 를 찾는다 | 깊이는 0 ~ D-1, 종합 대상은 「각 갈래의 마지막 노드」로 정의 |
| 5 | **멈춤 조건이 깊이뿐** | k 가 같은 자리를 맴돌아도 끝까지 돈다 | k 가 앞 단계와 같거나, 다른 갈래의 k 와 합쳐지면 조기 종료(「수렴」으로 기록) |
| 6 | **차원이 고정** | 주제와 안 맞는 축도 억지로 채운다 | 기본 4축에서 시작하되 맞지 않는 축은 이유를 적고 교체(예 : 사내 시스템 주제면 v3 → 조직·운영 비용) |
| 7 | **상태가 머릿속에만** | 중간 노드를 다시 볼 수 없고, 끊기면 처음부터 | R·k 를 표로 파일에 쓴다(아래 3-4) |
| 8 | **비용이 크다** | 4 × D 노드 + 종합. D=3 이면 노드 12개 | 가치가 있는 결정에만. 가벼운 질문은 D=1~2, 축 2~3개로 줄인다(`token-saving` 스킬) |

기본형은 의사코드처럼 쓰였지만 **한 번의 프롬프트 안에서는 모델이 루프를 「흉내」낼 뿐**이다. 진짜 루프로 돌리려면 노드마다 별도 호출을 하고, 상태를 디스크에 두고, 멈춤·검증을 바깥에서 판정해야 한다(§2).

### 3-3. 실행 절차 (보완판)

**모드 선택** — 사용자가 정하지 않으면 A 로 시작하고, 결정의 무게가 크면 B 를 제안한다.
- **A. 단일 세션 모드** (기본, 저비용) : 한 세션에서 순서대로 돈다. 단 3-2 의 1·3·4·5·7 보완은 반드시 적용
- **B. 실제 루프 모드** (고신뢰) : 갈래 V 마다 서브에이전트 1개(서로의 결과 비공개, 결과는 텍스트로 받아 메인이 저장) → 메인이 종합 → **다른 모델의 검토자**가 종합을 반박 검토

| 단계 | 할 일 | 됐는지 확인하는 법 |
|---|---|---|
| 0 | **설정** — 주제 · 축 V(교체 시 이유) · 깊이 D · 모드 · 예산(노드 수 상한)을 적고 사용자 확인 | 설정 블록이 파일 맨 위에 있다 |
| 1 | **가로 초기화** — 축마다 1차 분석 R[v][0] 과 핵심 변수 k[v][0] (근거 라벨 포함) | 축 수만큼 k 가 있고 모두 라벨이 붙었다 |
| 2 | **세로 재귀** — d = 1 … D-1 : 「k[v][d-1] 이 이 축에서 낳는 2차 구조적 결과와 그 작동 메커니즘」 → R[v][d], k[v][d]. 조기 종료 조건(수렴·`[확인 못 함]`)을 매번 확인 | 각 노드에 메커니즘(무엇이 어떻게 무엇을 낳나)이 한 줄 이상 있다 |
| 3 | **교차 종합** — 각 갈래 마지막 노드끼리 정성 행렬(+ / − / 0, 근거) · **모순(Paradox)** 목록 · 차원을 가로지르는 **최상위 레버리지 변수 1~3개** | 행렬의 모든 칸에 근거가 있고, 모순마다 「어느 축의 무엇과 무엇이 부딪히나」가 있다 |
| 4 | **검증** — A 모드 : 스스로 「가장 약한 고리 3개」를 찾아 적는다. B 모드 : 검토자의 반박을 받아 반영 | 약한 고리(또는 반박)와 처리 결과가 적혔다 |
| 5 | **보고** — 결론 먼저(레버리지 변수 · 모순 · 권고), 그 아래 트리 | 결론만 읽어도 무엇을 해야 하는지 안다 |

### 3-4. 상태 파일 형식 (A·B 공통)

```
# 분석 루프 — <주제>
설정 : 축 v1~v4(교체 내역) · D=<n> · 모드 A/B · 노드 상한 <n> · 시작 <날짜>

| 축 | d | 분석 R (요약) | 핵심 변수 k | 근거 | 메커니즘 | 상태 |
|----|---|---------------|-------------|------|----------|------|
| v1 | 0 | …             | …           | [실측] 출처 | A→B→C | 진행/수렴/중단 |

## 교차 행렬 (마지막 노드 기준)
|    | v1 | v2 | v3 | v4 |   ← 칸 : + / − / 0 + 한 줄 근거
## 모순
## 최상위 레버리지 변수
## 약한 고리 / 반박과 처리
```

완성 보고서는 정리본을 모아 두는 폴더에 `<제목>_YYYYMMDD` 이름으로 둔다(보관 위치는 자기 환경에 맞게 정한다).

## 4. 실패 유형 — 루프가 망가지는 자리

- **검증 연극** : 검증자가 독립적이지 않아 증거 없이 「완료」를 선언한다
- **오류 누적** : 무인 실행 중 실수가 다음 단계의 입력이 된다(분석 루프의 깊이 방향이 특히 취약)
- **무한 루프·비용 폭주** : 멈춤 조건이 영영 충족되지 않는다 → 반복 상한 · 예산 · 일시정지 장치
- **이해 부채·인지 포기** : 루프가 만든 결과를 읽지 않아 사람의 이해와 산출물 사이가 벌어진다. 루프는 생각을 빠르게 하려고 쓰지, 생각을 피하려고 쓰지 않는다
- **충돌** : 병렬 에이전트가 같은 파일을 쓴다 → worktree 격리
- **하네스 단조 증가** : 루프마다 규칙·문서를 덧붙이기만 한다 → 새 규칙을 넣을 때 무엇을 뺄지 함께 정한다

## 5. 다른 스킬과의 관계

- `token-saving` — 루프는 토큰을 빠르게 태운다. 서브에이전트는 두 번째 의견이 비용값을 할 때만
- `/loop`·`/schedule`·Workflow — 실행 루프를 실제로 돌리는 Claude Code 기능. Workflow 는 사용자가 명시적으로 요청할 때만
