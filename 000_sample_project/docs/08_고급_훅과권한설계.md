# 08 고급 — 훅과 권한 설계 : 「부탁」을 「강제」로 바꾸기

> CLAUDE.md는 부탁이다. 클로드가 대부분 지키지만 100%는 아니다. **반드시 지켜야 하는 것**은 권한 설정과 훅으로 옮긴다.
> 설정 이름·이벤트 이름은 버전에 따라 바뀔 수 있다. 문서와 다르면 공식 문서(https://code.claude.com/docs)가 맞다.

## 1. 한눈에 보기

| 수단 | 성격 | 이럴 때 | 위치 |
|---|---|---|---|
| **CLAUDE.md** | 부탁(대개 지킴) | 말투, 코드 습관, 작업 순서 | `CLAUDE.md` |
| **권한 규칙** | 강제(도구 호출 자체를 막거나 묻게 함) | 비밀 파일 읽기 금지, 강제 푸시 금지 | `.claude/settings.json`의 `permissions` |
| **훅** | 강제 + 자동 실행(내 스크립트가 끼어듦) | 저장 뒤 자동 정리, 위험 명령 검사, 끝내기 전 시험 확인 | `.claude/settings.json`의 `hooks` |

고르는 기준 : **어기면 사고가 나는가?** → 권한·훅. **어겨도 고치면 되는가?** → CLAUDE.md.

## 2. 설정 파일의 층

여러 곳의 설정이 겹치면 **더 좁고 더 강한 쪽**이 이긴다. 대략 이 순서다(위가 강함).

1. 회사가 배포한 관리 설정(managed) — 개인이 못 바꾼다
2. 실행할 때 준 명령줄 옵션
3. `.claude/settings.local.json` — 내 컴퓨터에서만, 커밋하지 않는다
4. `.claude/settings.json` — 팀이 같이 쓴다, 커밋한다
5. `~/.claude/settings.json` — 내 모든 프로젝트 공통

- 팀 규칙은 4번에, 내 취향은 3·5번에 둔다.
- `deny`는 어느 층에 있든 이긴다. 막아야 할 것은 `deny`로 쓴다.

## 3. 권한 규칙 짜는 법

이 틀의 `.claude/settings.example.json`이 출발점이다.

| 칸 | 뜻 | 넣을 것 |
|---|---|---|
| `deny` | 절대 못 함 | `.env`·키 파일 읽기, 강제 푸시(`--force`·`-f`), `rm -rf`·`rm -fr` |
| `ask` | 할 때마다 물음 | `git push`, 배포, 패키지 발행, 그 밖의 `rm` |
| `allow` | 묻지 않고 함 | `git status`·`git diff`처럼 읽기만 하는 명령, 시험 명령 |

- **처음엔 좁게** 시작해서, 매번 승인하게 되는 안전한 명령만 `allow`로 옮긴다.
- 「모든 것 허용」 모드(`bypassPermissions`)는 **버려도 되는 격리 환경**(컨테이너, 클라우드 세션)에서만 쓴다. 내 컴퓨터에서 켜지 않는다.
- `Read(./.env)` deny 는 읽기 도구뿐 아니라 Bash 의 `cat`·`head`·`tail`·`sed`·`tee` 와 `< .env`·`> .env` 같은 방향 바꾸기에도 적용된다. 다만 파이썬·노드 스크립트가 직접 여는 것이나 `grep -r 키 .` 처럼 파일 이름을 적지 않는 명령은 막지 못한다. 비밀값은 아예 저장소 밖에 두는 것이 먼저다.
- ⚠ **Bash 규칙은 명령 글자를 비교한다.** `Bash(git push --force *)` 하나만 쓰면 `git push -f origin main` 과 `git push origin main --force` 는 deny 에 걸리지 않는다(실제로 시험했다). 그래서 예시는 강제 푸시를 네 가지 모양으로 막고(`--force*`, `-f*`, `* --force*`, `* -f*`), `rm` 은 흔한 두 모양을 막은 뒤 나머지를 `ask` 로 받는다. 그래도 `/bin/rm`·`sh -c '…'` 같은 모양까지 막지는 못한다. **deny 는 흔한 실수를 막는 장치이지 보안 벽이 아니다.** 벽이 필요하면 샌드박스를 쓴다.

## 4. 훅

훅은 클로드가 어떤 일을 하기 **전·후**에 내 명령을 자동으로 실행한다.

| 이벤트 | 언제 | 대표 쓰임 |
|---|---|---|
| `PreToolUse` | 도구를 쓰기 직전 | 위험한 명령 검사 후 막기 |
| `PostToolUse` | 도구를 쓴 직후 | 파일을 고친 뒤 자동 정렬(포매터)·린트 |
| `UserPromptSubmit` | 내가 말을 보낸 직후 | 날짜·브랜치 같은 맥락 덧붙이기 |
| `Stop` | 클로드가 「끝」이라고 하려 할 때 | 시험 통과·커밋 여부 확인, 안 됐으면 계속 시키기 |
| `SessionStart` | 세션을 열 때 | 의존성 설치, 상태 안내 |

**막는 법** : 훅 명령이 종료 코드 `2`로 끝나면 그 동작이 막히고, 표준 에러에 쓴 글이 클로드에게 전달된다. 클로드는 그 글을 읽고 고쳐서 다시 한다.

예시는 이 틀의 `.claude/settings.hooks.example.json`에 있고, 막는 훅 두 개는 스크립트로 `.claude/hooks/`에 있다.
- 파일을 고친 뒤 포매터 돌리기(PostToolUse)
- 비밀값 파일(`.env`, `.env.local`, `prod.env` …)을 건드리는 Bash 명령 막기 — `hooks/block-env.sh`. 견본 `.env.example` 은 허용
- 끝내기 전에 커밋 안 된 변경이 있으면 **한 번** 알리기 — `hooks/stop-uncommitted.sh`

한 줄짜리 훅 명령은 읽기도 시험하기도 어렵다. 스크립트로 빼고 `bash .claude/hooks/test-hooks.sh` 로 시험한다(막아야 할 것·통과시켜야 할 것·도구가 없을 때·Stop 재촉 여부 19가지).

### 막는 훅을 만들 때 지킬 세 가지

1. **도구가 없으면 막는다(fail-closed).** 훅이 쓰는 `jq` 같은 도구가 없으면 명령이 실패하는데, 종료 코드가 2가 아니면 클로드 코드는 그냥 진행한다. 검사를 못 했으면 통과가 아니라 막아야 한다. `block-env.sh` 는 처음에 `jq` 가 있는지 보고, 없으면 종료 코드 2로 「jq 를 설치하라」고 알린다.
2. **Stop 훅은 `stop_hook_active` 를 본다.** Stop 훅에 막혀 클로드가 계속하는 중이면 입력의 `stop_hook_active` 가 `true` 다. 이때도 막으면 같은 재촉이 되풀이된다. `stop-uncommitted.sh` 는 한 번 알리고, 두 번째부터는 보내 준다.
3. **이름 맞추기는 넓게, 예외는 좁게.** `.env` 만 보면 `prod.env` 를 놓치고, 끝에 `.env` 만 보면 `.env.example` 까지 막는다. 막을 모양과 허용할 모양을 시험 목록으로 먼저 적고 맞춘다.

> **실제 사례** : 이 저장소를 만든 클라우드 세션에는 「커밋 안 된 변경이 있으면 끝내지 못하게 하는」 `Stop` 훅이 걸려 있었다. 덕분에 작업이 컨테이너와 함께 사라지는 일이 없었다. 반대로 일부러 커밋을 미뤄야 할 때(다른 작업이 파일을 쓰는 중)는 훅이 계속 재촉했다. 이 틀의 처음 예시도 같은 문제가 있었다. 「커밋하지 말라」고 지시한 채 헤드리스로 돌려 보니 같은 재촉이 11번 되풀이됐다(14차례). `stop_hook_active` 를 보게 고친 뒤에는 1번 알리고 끝났다(3차례). **훅을 만들 때는 예외 상황도 같이 설계한다.**

## 5. 주의

1. **훅은 내 권한으로 실행된다.** 남이 준 훅 설정은 스크립트를 한 줄씩 읽고 나서 쓴다.
2. **훅은 빨라야 한다.** 매 도구 호출마다 돌기 때문에, 몇 초씩 걸리는 훅은 작업 전체를 느리게 한다. 오래 걸리는 시험은 `Stop`에만 건다.
3. **실패 메시지를 친절하게.** 「막힘」 대신 「`npm test`가 3개 실패했다. 고친 뒤 다시 끝내라」처럼 다음 할 일을 쓴다. 클로드가 그 글을 읽고 움직인다.
4. 훅을 바꾼 뒤에는 일부러 걸리는 상황을 만들어 **정말 막히는지 시험한다.** 이 틀에서는 `bash .claude/hooks/test-hooks.sh`. 처음 쓴 스크립트는 명령 끝의 `.env` 를 놓쳤는데(셸의 `while read` 가 줄바꿈 없는 마지막 낱말을 버림), 이 시험이 바로 잡았다.
