# 10 고급 — 에이전트 팀과 병렬 작업 : 여러 일을 동시에 맡기기

> 서로 관계없는 일 여러 개는 서브에이전트(또는 세션)에 **동시에** 맡기면 빨라진다. 대신 일을 나누고, 지시문을 쓰고, 결과를 검증하는 일은 여전히 내(메인 세션) 몫이다.
> 서브에이전트 기본은 `docs/04`, 세션 여러 개의 기본 규칙은 `docs/07`에 있다.

## 1. 언제 나누나

| 나누면 좋은 일 | 나누면 손해인 일 |
|---|---|
| 서로 다른 폴더의 독립 작업(샘플 여러 개, 모듈별 시험) | 파일 몇 개짜리 작은 수정 |
| 많이 읽고 결론만 필요한 조사 | 단계마다 내 판단이 필요한 일 |
| 독립적인 검토(내 생각에 물들지 않은 눈) | 같은 파일을 여럿이 고쳐야 하는 일 |

판단 기준 : **나눠도 서로 기다리지 않는가?** 그렇다면 나눈다.

## 2. 지시문(브리프) 쓰는 법

서브에이전트는 내 대화를 모른다. **지시문이 그 아이가 아는 전부**다.

```markdown
## 목표
[무엇을 만들거나 알아낼지 한두 줄]

## 범위
- 작업 폴더 : [경로] — 이 폴더 밖은 절대 수정하지 말 것
- 하지 말 것 : git add/commit/push, 다른 폴더 수정

## 규칙
- [CLAUDE.md의 핵심 규칙 몇 줄 — 서브에이전트는 자동으로 다 지키지 않을 수 있다]

## 완료 조건
- [실행해서 통과시킬 명령]
- [직접 확인할 것 : 화면 캡처, 실제 입력으로 실행]

## 보고 형식
파일 목록, 실행한 명령과 결과(통과 개수), 남은 문제
```

- **범위를 못 박는다.** 여럿이 동시에 일하면 공용 파일(루트 README, 설정)을 서로 덮어쓴다. 공용 파일은 메인 세션만 고친다.
- **완료 조건을 명령으로** 준다. 「잘 만들어 줘」가 아니라 「`npm test`가 통과할 것」.
- **이미 알아낸 것과 해 본 것**을 적어 준다. 같은 실패를 되풀이하지 않게.
- **근거를 그대로 적게** 한다. 「테스트 있음」이면 파일 경로와 테스트 이름을 글자 그대로. 그래야 3절의 확인이 몇 분 안에 끝난다(아래 사례).

## 3. 결과는 반드시 다시 확인한다

서브에이전트의 보고는 자신만만한 말투로 온다. 틀린 것도 마찬가지다.

1. 보고에 적힌 시험 명령을 **내가 직접 다시 돌린다.**
2. 화면이 있는 결과물은 **내가 직접 캡처해 본다.**
3. 보고가 「마지막에 조금 고쳤고 그 뒤로는 확인 안 함」이라고 하면, 그 부분을 꼭 본다.
4. 확인한 뒤에 한꺼번에 커밋한다.

> **실제 사례** : 이 저장소의 실습 샘플 `001`~`007`은 서브에이전트 7개에 동시에 맡겨 만들었다. 메인 세션은 다음 일을 했다.
> - 폴더마다 범위를 못 박았다.
> - 끝난 뒤 폴더를 최종 위치(`000_sample_project/001_…`)로 옮겼다.
> - **7개 시험을 모두 다시 돌렸다**(254개 통과).
> - 옛 경로가 남은 README를 고쳤다.
>
> `009`는 서브에이전트가 마지막 CSS 수정 뒤 화면을 다시 보지 않았다고 보고했다. 그래서 메인 세션이 직접 캡처해 확인했다.

> **두 번째 사례(읽기 전용 점검 3개 동시)** : 샘플 `003`·`004`·`006`의 「README 약속 ↔ 테스트」 점검을 읽기 전용 에이전트 3개에 동시에 맡겼다(각 약 30초, 약 5만 8천 토큰). 브리프에 「근거로 테스트 이름을 그대로 적는다」를 넣었더니, 메인 세션은 인용된 테스트 이름 14개를 `grep` 으로 1분 안에 모두 확인할 수 있었다(14개 모두 실제로 있었다). 「테스트 없음」 판정도 표본으로 테스트 본문을 열어 맞는지 봤고, 확인된 빈칸 둘(004 커피 +5점·1.6배, 003 빈 PATCH → 400)은 테스트로 메웠다. 그 뒤 12개 샘플 시험을 모두 다시 돌렸다(548개 통과, 건너뜀 0). 이번엔 틀린 보고가 없었지만, **확인하지 않았다면 그 사실도 알 수 없었다.**

## 4. 「읽기만 하는」 에이전트를 정말 읽기만 하게

`.claude/agents/reviewer.md` 처럼 「읽기만 한다」고 적은 에이전트도 `tools` 에 Bash 가 있으면 파일을 고칠 수 있다. 지시문은 부탁이다.

| 방법 | 막히나 | 이유 |
|---|---|---|
| 지시문에 「읽기만 한다」 | 부탁 | 대개 지키지만 강제가 아니다 |
| `tools` 에서 Write·Edit 빼기 | 일부 | Bash 로 `touch`, `sed -i` 를 할 수 있다 |
| 에이전트 설정 `permissionMode: plan` | 조건부 | 메인 세션이 `acceptEdits`·`auto`·`bypassPermissions` 이면 **무시**된다 |
| 에이전트 파일 안(frontmatter) 훅 | 조건부 | 폴더를 신뢰한 대화형 세션에서만 돈다. `-p` 헤드리스에서는 **건너뛴다** |
| **`settings.json` 훅 + `agent_type`** | 강제 | 서브에이전트 안에서도 돌고, 입력에 에이전트 이름이 들어 있다 |

이 틀의 `.claude/hooks/readonly-agent-bash.sh` 가 마지막 방법이다. `reviewer` 에이전트의 Bash 만 `git diff·status·log·show·blame`, `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg` 로 묶고, 명령을 잇거나 파일로 내보내는 기호(`` ; & | > < ` $ ``)를 막는다. 메인 세션과 다른 에이전트는 건드리지 않는다. 시험 : `bash .claude/hooks/test-hooks.sh`.

> **실제 시험** : 편집 자동 승인 모드의 헤드리스 세션에서 「시키는 명령을 그대로 실행하는」 시험용 `reviewer` 에이전트에게 `git status` 와 `touch reviewed.txt` 를 시켰다. 훅이 없을 때는 파일이 생겼고, 훅을 `settings.json` 에 걸자 `touch` 만 「reviewer 에이전트는 읽기만 한다」로 막혔다.

## 5. 격리 : worktree와 클라우드 세션

| 방식 | 격리 수준 | 쓰임 |
|---|---|---|
| 같은 폴더, 다른 하위 폴더 | 낮음 | 폴더가 확실히 나뉘는 일 |
| git worktree | 중간 — 브랜치마다 작업 폴더가 따로 | 같은 저장소의 다른 기능을 동시에 |
| 클라우드 세션 | 높음 — 컨테이너가 따로 | 오래 걸리는 일, 내 컴퓨터를 건드리면 안 되는 일 |

## 6. 비용 감각

- 서브에이전트 하나하나가 **처음부터 파일을 읽는다.** 7개를 띄우면 읽기 비용도 대략 7배다.
- 그래서 「작고 많은 일」보다 **「크고 독립적인 일 몇 개」**로 나눈다.
- 결과 요약은 짧게 요구한다. 긴 보고서는 메인 세션의 맥락을 다시 채운다.
