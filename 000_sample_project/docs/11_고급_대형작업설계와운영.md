# 11 고급 — 대형 작업 설계와 운영 : 며칠짜리 일을 맡기는 법

> 「앱 하나 만들어 줘」 같은 큰일을 한 번에 시키면, 처음엔 그럴듯하다가 중간부터 무너진다. 큰일은 **계획 → 작은 단위 → 단위마다 검증 → 기록**으로 쪼개서 굴린다.

## 1. 한눈에 보기

| 단계 | 할 일 | 남길 것 |
|---|---|---|
| 1. 계획 | 계획 모드로 먼저 설계만 받는다 | `docs/plan.md` : 목표, 범위, 단계, 완료 조건 |
| 2. 쪼개기 | 하루 안에 끝나고 시험할 수 있는 단위로 | 단계 목록(체크박스) |
| 3. 단위 실행 | 한 단위씩, 끝날 때마다 시험 + 커밋 | 커밋 하나 = 단위 하나 |
| 4. 기록 | 결정한 것, 실패한 것, 남은 것 | `docs/plan.md` 갱신, 인계 메모 |
| 5. 점검 | 실제 입력으로 끝까지 돌려 보기 | 캡처, 실행 로그 |

## 2. 계획을 먼저 받는다

- 계획 모드(plan mode)로 「아직 고치지 말고 계획만 세워」라고 시킨다. 계획을 읽고 고친 뒤에 실행을 허락한다.
- 계획서에 꼭 넣을 것 :
  1. **하지 않을 것**(범위 밖) — 이게 없으면 일이 끝없이 커진다
  2. **완료 조건**(명령으로 확인 가능한 것)
  3. **모르는 것** — 시작 전에 사람이 답해야 할 질문
- 계획서는 파일로 남긴다. 대화는 압축되거나 끊기지만 파일은 남는다.

## 3. 맥락(컨텍스트) 관리

긴 작업에서 가장 흔한 실패는 **앞에서 정한 것을 뒤에서 잊는 것**이다.

| 증상 | 처방 |
|---|---|
| 앞에서 정한 규칙을 어긴다 | 그 규칙을 `CLAUDE.md`나 계획서로 옮긴다 |
| 같은 파일을 반복해서 읽는다 | 요약을 파일로 남기고 그 파일을 읽게 한다 |
| 대화가 길어져 느리고 비싸다 | 한 단위가 끝나면 기록을 남기고 `/clear` 후 기록을 읽고 다시 시작 |
| 하위 폴더마다 규칙이 다르다 | 하위 폴더에 `CLAUDE.md`를 따로 둔다(그 폴더에서 일할 때 함께 읽힌다) |

- `/context`로 무엇이 맥락을 차지하는지 보고, 안 쓰는 MCP·스킬을 끈다(`docs/06` 참고).

## 4. 단위마다 검증한다

- 단위가 끝날 때마다 **시험 → 실제 실행 → 커밋**. 시험이 통과해도 실제로 돌려 본다.
- 실패하면 고치기 전에 **원인부터 한 줄로 적게** 한다. 원인을 모른 채 고치면 같은 문제가 다른 곳에서 터진다.
- 되돌리기 쉬워야 한다 : 단위마다 커밋해 두면 `git revert` 한 번으로 돌아간다.

> **실제 사례 — 시험 통과 ≠ 동작함** : 이 저장소의 유튜브 분석 도구는 시험 38개를 모두 통과한 상태로 커밋됐다. 그런데 실제 영상에 처음 돌리자 문제가 세 겹으로 나왔다.
> 1. 영상 포맷이 없었다.
> 2. 자막을 여러 언어로 받다가 요청 제한(429)에 걸렸다.
> 3. 영상 다운로드가 서버 IP 차단(403)으로 막혔다.
>
> 하나씩 원인을 찾아 고치고, 실패 상황을 재현하는 시험을 더했다(38 → 48개). **현실 입력으로 한 번 돌려 보는 것**이 시험 수십 개보다 많은 것을 알려 줬다.

## 5. 사람이 결정할 것은 사람에게

긴 작업일수록 클로드가 혼자 정해 버리기 쉬운 결정이 생긴다. 아래는 **멈추고 묻게** 한다.

- 라이선스·저작권(예 : 묶음은 판매 금지, 샘플 코드는 MIT로 나누기)
- 공개 범위(공개 저장소에 무엇을 올릴지)
- 되돌리기 어려운 일(배포, 데이터 삭제, 기본 브랜치 변경)
- 비용이 크게 드는 일(대량 병렬 작업, 유료 API 대량 호출)

`CLAUDE.md`에 「이런 결정은 먼저 묻는다」를 한 줄 넣어 두면 덜 놓친다.

## 6. 끝낼 때

- `done-check` 스킬로 증거를 모은다(요청 대조, 실행 결과, 캡처, `git diff --stat`, 남은 문제).
- 계획서의 체크박스를 갱신하고 **남은 일**을 적는다. 다음 세션(또는 다음 사람)이 거기서 시작한다.
